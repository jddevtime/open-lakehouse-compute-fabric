### F01 Job credentials expand the submitting token permissions (P1)

* **Reproduced:** yes. Against the pre-fix source the new tests fail (a derived job token regains `secret.use` and `lakehouse.write` that the submitting PAT excluded).
* **Changed:** a job or session now stores the submitter's credential ceiling in `spec["credential"]` (`security/rbac.py`: `Principal.credential_ceiling`, `workspace_lock`, `fixed_ceiling`, `SQL_KERNEL_PERMISSIONS`, `LEGACY_JOB_PERMISSIONS`). The callback token is minted by `TokenService.create_derived` (`security/tokens.py`; `compute/jobs.py::_mint_job_token`, `compute/sessions.py`) and `api/deps.py::_bind_derived_credential` rebuilds the principal on every request as: the owner's *current* role bindings, intersected with the `job` scope and the stored ceiling, locked to the job's workspace, and valid only while the origin PAT or login session, the attempt (`attempt == meta.attempt`, job not terminal) or the kernel session is alive. A malformed ceiling fails closed; jobs submitted before ceilings were persisted get a read-only legacy ceiling. A job that references secrets re-requires `secret.use` of the current owner at dispatch. Pooled hidden SQL kernels get a fixed read-only ceiling. Pipelines store `principal_credential` and raise `credential_revoked` when the origin is revoked (`pipelines/service.py`, `pipelines/engine.py`). `POST /v1/identity/tokens` refuses a token that asks for more than the calling token holds (`api/core/identity.py`).
* **Tests:** `tests/compute/test_job_credentials.py` (11: restricted PAT cannot use secrets or write; unrestricted Contributor keeps the documented job capabilities; Viewer gains nothing; workspace binding; org-level Contributor stays bound; revoked parent PAT; revoked login; finished job / stale attempt; session kernel credential; mint subset rule), `tests/orch/test_pipeline_credentials.py` (3).
* **Behaviour change:** logging out, or revoking the PAT a job was submitted with, ends the running job's callbacks (state, results, lakehouse access). Long-running jobs should be submitted with a service PAT.
* **Residual risk:**
  * The tests drive the controller and the API directly with test agents.
  * The ceiling limits what the *callback token* can do. The notebook still runs as the worker's OS user and holds `job.json` (token, resolved secrets); see "Execution isolation" below.
  * **Token registration window (closed in the residual-fixes pass).** `job_attempts.token_id` used to be written only after `provider.submit` returned. It is now recorded straight after the token is minted and before the spec is built or the provider is called, and `_launch_failed` revokes the attempt's token at once, so a failed hand-off (including the `WorkerOffline` requeue, which does not end the attempt) leaves no live credential; tests: `tests/compute/test_job_credentials.py` (provider that raises in `submit`: id recorded before the call, token revoked and refused with 401; requeue: the abandoned attempt's token is dead, the next attempt's works). What remains: a controller that dies in the few statements between minting and the record, which leaves a token for the job timeout plus one hour (it is still refused once the attempt is no longer live), and an *uncertain* remote submission (Livy/Fabric adoption) deliberately keeps its token because the remote job may be running with it.
  * Session and pipeline derivation were audited and tested at the same level as jobs (test doubles); there may be other derivation sites we did not find.

### F02 Read-only Spark SQL accepts host capability expressions (P1)

* **Reproduced:** yes. On the pre-fix planner `reflect(...)`, `java_method(...)` and `SELECT TRANSFORM('hello') USING 'cat'` were all classified as read-only selects. We did not repeat the reviewer's Spark 4.1.1 engine probe; we rely on the review for the engine capability.
* **Changed:** `sql/guard.py` now applies to every statement and every role (writers included): script transformation, `REFLECT` / `JAVA_METHOD` / `TRY_REFLECT` / `CALL_FUNCTION` / `IDENTIFIER()`, `INSERT OVERWRITE [LOCAL] DIRECTORY`, `LOCATION`, `USING <datasource>` paths and file queries (`parquet.\`path\``), `CREATE FUNCTION`, `SET`, `USE`, `LOAD DATA`, `${...}` substitution (scanned on the raw text, because Spark substitutes before parsing), a denylist of host-reaching scalar functions (`SPARK_DENIED_FUNCTIONS`, prefixes `read_`, `http_`, `ai_`, `remote_`) and an **allowlist** of table functions (`SPARK_ALLOWED_TABLE_FUNCTIONS`, `DUCKDB_ALLOWED_TABLE_FUNCTIONS`). Text that sqlglot cannot parse is refused for callers without `sql.write`. Spark runs the *rendered* SQL, so `sql/service.py::_plan_spark` re-checks the rendered text (`guard.check_final_sql`). `compute/sessions.py::run_spark_sql` calls `guard.check_spark_sql` before any pooled session is looked up or created. DuckDB: file readers are served by OLCF, other table functions are an allowlist, quoted file names are refused.
* **Tests:** `tests/data/test_sql_host_guard.py` (138: the review's statements, obfuscated spellings, parameter smuggling, accepted ordinary queries), `tests/compute/test_sql_session_guard.py` (8: refused before any session exists, `WITH .. INSERT` behind a Viewer, writers get the same function rules). We also confirmed on a running server that `POST /v1/sql/execute` answers `422 unsupported` for the review's three statements, a path table and `ADD JAR`.
* **Residual risk:**
  * ~~Scalar functions are a denylist~~ Closed by C01 of the second external review: Spark functions are now an allowlist (`olcf.sql.spark_functions`), qualified/unknown/UDF calls are refused, and unparsed text is no longer forwarded for any role. A genuine built-in missing from the list is refused until reviewed and added.
  * Not run through the authenticated endpoint into a pooled Spark kernel on the supported runtime (the review's "regression check" asks for it); the kernel-door tests use test compute.
  * Defence-in-depth gap found while documenting (closed in the residual-fixes pass): `guard.check_spark_sql(sql, strict=False)` accepted statements sqlglot parses as generic commands or bare nodes (`ADD JAR`, `ADD FILE`, `RESET`, `CACHE TABLE`, `CLEAR CACHE`, `CALL`, `OPTIMIZE`...) for a caller with `sql.write`, so a direct `ComputeService.run_spark_sql` could reach them. The guard itself now refuses every statement that is not a read or one of the DML/DDL kinds the SQL service routes to Spark (`SPARK_ALLOWED_KINDS`), `strict` or not, and judges text it cannot parse fragment by fragment (leading keyword allowlist; no `JAR`/`ARCHIVE`/`LOCATION`/`DIRECTORY`); `SHOW ...` is classified as the read it is. Tests: `tests/data/test_sql_host_guard.py` (session-command class, writer DML/DDL kept, reads kept, fail-closed text) and `tests/compute/test_sql_session_guard.py` (direct `run_spark_sql` as org admin, Contributor and Viewer: refused, no session created; writers' INSERT/CTAS/CREATE TABLE/MERGE/UPDATE/DELETE/DROP still run). The SQL service already refused the `unsupported` kind first, so REST/MCP/SDK/UI were never affected.

### F03 The default Kubernetes runner writes into a read-only volume (P1)

* **Reproduced:** source-confirmed. The pre-fix provider mounted the Secret at `/opt/olcf/job` read-only and the runner wrote `result.json` next to `job.json`. No cluster was available to us either.
* **Changed:** `compute/providers/kubernetes.py` and `runtime_lib/runner.py`. The Secret `input` is mounted read-only at `/opt/olcf/input` (mode `0440`); an `emptyDir` `work` at `/opt/olcf/work` (optional size limit) and an `emptyDir` at `/tmp`; the command is `python -m olcf.runtime_lib.runner --workdir /opt/olcf/work /opt/olcf/input/job.json`, where `--workdir` stages the input into the writable directory (owner-only files) and deletes the staged `job.json` when the run ends. The pod is non-root (`runAsNonRoot`, `runAsUser` 10001 by default, `fsGroup`, no privilege escalation, all capabilities dropped, `RuntimeDefault` seccomp); `read_only_root_filesystem` is a config option, off by default. `spark_submit` mode got the same input/work split, but its entrypoint is expected to call the runner with `--workdir` and that part is not tested.
* **Tests:** `tests/compute/test_review_k8s.py` (25), `tests/compute/test_providers_k8s.py`, `tests/node/test_runner_remote.py` (9). `FakeKube` (`tests/compute/fake_kube.py`) is a test API server **and** kubelet: it mounts Secrets read-only whatever the mount says (writes fail with `EROFS` through an audit hook, because the sandbox runs as root), runs the pod command with the real runner and turns output into timestamped pod logs.
* **Residual risk:** File ownership under a non-root UID with `fsGroup`, `readOnlyRootFilesystem: true`, the image contract (runtime venv with `olcf` installed `--no-deps`) and `spark_submit` mode are to be confirmed on a cluster.

### F04 Livy retries writes after ambiguous transport failures (P1)

* **Reproduced:** yes. A `MockTransport` that loses the response of the first statement POST produced two POSTs on the pre-fix client and returned the second statement id; on the current client it raises `SubmissionUncertain` after one POST.
* **Changed:** `compute/providers/livy.py`. Per-operation retry: GET/DELETE retry on transport errors and 5xx; POST retries only when the request provably did not leave (`ConnectError`, `ConnectTimeout`, `PoolTimeout`, `UnsupportedProtocol`) or on `429` (a `503` answer is ambiguous since external review C02: it raises `SubmissionUncertain` like any other 5xx); every other POST failure raises `SubmissionUncertain` (`submission_uncertain`, `ProviderError.uncertain`). Sessions and batches are named `olcf-<job>-a<attempt>`; the intent is persisted (`provider_handle.sent=false`) before the create request leaves; a restarted controller reconciles by name (`recover()`), and the outcome codes are `submission_adopted`, `submission_not_created` (absent for `submission_quiesce_seconds`, default 60: failed and retried), `submission_unresolved` (unknown for `submission_reconcile_seconds`, default 900: failed, never retried automatically). There is no new job state; uncertainty is an event and a code on `provisioning`/`running`.
* **Tests:** `tests/compute/test_review_livy.py` (21), `tests/compute/test_providers_livy.py`.
* **Residual risk:** How a Livy gateway behaves when a statement is accepted and the connection drops (and whether `GET /sessions/{id}/statements` always shows it) is the assumption the reconciliation rests on. Unresolved submissions need an operator.

### F07 The Kubernetes completion result is never transmitted by the stock runner (P2)

* **Reproduced:** yes (pre-fix `finish()` wrote `result.json` and emitted only `runner_finished`; the controller wanted an `event == "result"`).
* **Changed:** one explicit contract (`ComputeProvider.result_contract`: `"runner"` for Kubernetes, `"provider"` for Livy, external and Fabric). In remote mode (`--workdir` or `--remote`) the runner, *after* persisting `result.json` atomically, uploads declared artifacts to `POST /v1/jobs/{id}/artifacts/{name}` (3 tries), prints exactly one `@@OLCF@@ {"event":"result",...}` line, then `runner_finished`, and writes a compact record (at most 3.5 KiB) to `/dev/termination-log`. The event line is capped (`limits.result_event_bytes`, default 192 KiB); a larger document is shortened, carries `result_ref`, and the complete one is uploaded as artifact `result.json`. The controller no longer invents a success: a terminal application whose result did not arrive is *incomplete*; the monitor tries `find_result` (tail of the retained output, independent of the log cursor) and the termination record, waits `compute.remote_result_grace_seconds` (default 120) and then fails the attempt with `failure.details.code = "result_missing"` (category `provider`, not retried unless the job is `idempotent`). The agent runner is byte-for-byte unchanged without the flags.
* **Tests:** `tests/node/test_runner_remote.py` (9), `tests/compute/test_review_k8s.py`; `tests/compute/test_real_agent.py` and `tests/node/test_agent_jobs.py` pass unchanged.
* **Residual risk:** `FakeKube` only. The termination message size, `terminationMessagePolicy: File` and the artifact upload from inside a pod (network policy, token, TLS trust of the controller URL) are not observed on a cluster.

### F08 Remote log paging can discard the final result and later log lines (P2)

* **Reproduced:** partly. The terminal-page omission is visible in the pre-fix monitor (one page, then finish, `eof` unchecked). The bounded-window loss was shown by the reviewer with a provider model; ours was a model too, not a live Kubernetes log server.
* **Changed:** `compute/jobs.py::_poll_remote` separates "the process ended" from "the output was drained": up to `compute.remote_log_pages_per_poll` (16) pages of 256 KiB per poll, finish only at provider `eof`, bounded by `compute.remote_drain_timeout_seconds` (300) after which a visible `log_gap` event and a job-log note are written. The offset and the provider's opaque cursor are persisted after every page; a page is written as `log_pending {seq, chars}` first, so a stop between "written" and "cursor saved" re-reads exactly that page and the log store (which ignores a repeated `seq`) cannot duplicate it. The Kubernetes provider now reads with `--timestamps --since-time=<second of the cursor> --limit-bytes=...` and a timestamp + count + hash cursor, reports a missing anchor as `LogsPage.gap`, grows the window x4 up to 64 MiB for a burst within one second, and beyond that steps over the second with an explicit gap.
* **Tests:** `tests/compute/test_review_k8s.py` (rotation, truncation, restart in the middle of a page, more than 256 KiB with the result at the end, more than the window).
* **Residual risk:**
  * To be confirmed on a kubelet: how it splits lines longer than the runtime's 16 KiB records and where it puts timestamps; output rotated away *before the first read* cannot be detected (nothing to compare with).
  * **Dense log bursts are quadratic.** Each page re-reads the retained log from the second of the cursor, so a job that writes many MiB inside one second is re-fetched for every page (up to the 64 MiB window), and the work grows with the square of the burst. Bounded by the window and the drain timeout, but real.
  * The python Kubernetes client has no `since_time`, so the provider derives `since_seconds` and over-reads by two seconds (de-duplicated by the cursor).
  * The absolute guarantee is only as good as the pod's retained log; the termination record and `result` event are the backstops for the result, not for every log line.

### F13 A timed-out pipeline activity can overlap its retry (P1)

* **Reproduced:** yes. The new test fails on the pre-fix engine, and the review's timing evidence matches the source order (conclude, schedule retry, then signal cancel).
* **Changed:** `pipelines/engine.py`, `pipelines/activities/base.py`, `pipelines/activities/http.py`, `pipelines/ssrf.py`, `pipelines/model.py`, `schemas/pipeline-v1.json`. A timeout now enters a *cancelling* phase (`Task.timed_out`): cancel callbacks run (`ActivityContext.on_cancel`; the `http` activity aborts its sockets through the SSRF `ConnectionTracker`; async activities get the `cancel` hook every 2 s and are polled to a terminal state), and the engine waits up to `policy.cancelGraceSeconds` (default 30, 0 to 3600; engine constructor `timeout_cancel_grace_seconds`) before it concludes the attempt. It stopped: `timeout`, retryable per `retries`. It did not stop, was cancelled where the other side may have done the work (`ActivityCancelled(uncertain=True)` or a `*_uncertain` category), or completed after the deadline: `timeout_uncertain`, retryable **only if idempotent** (`policy.idempotent`, an idempotent class, or an `http` request with an `Idempotency-Key`); otherwise the run fails with `details.operatorAction` and the decision is `POST /v1/pipeline-runs/{id}/resume`. Each uncertain outcome publishes `pipeline.activity.outcome_uncertain`, increments `olcf_pipeline_activity_outcome_uncertain_total{type,category}` and is logged. HTTP: not-sent failures are always repeatable; sent-but-unanswered failures repeat for `GET/HEAD/OPTIONS` only; `408/425/429` are retried for every method (`503` no longer, since external review C03); a `5xx` that may have been processed is not retried for non-safe methods unless idempotent; `typeProperties.idempotencyKey` is sent unchanged on every attempt.
* **Behaviour change:** a non-idempotent activity that times out no longer retries on its own, even with `retries > 0`; it fails and waits for an operator.
* **Tests:** `tests/orch/test_timeout_overlap.py` (23: non-cooperative activity, idempotent retry after stop, grace expiry, per-engine default, schema validation, job activity whose cancel is never acknowledged, accepted-but-unanswered POST, PUT/PATCH/DELETE, idempotency keys, aborted blocked reads, never-sent requests, resets, 5xx handling, run cancel), `tests/orch/test_schema_cache.py`.
* **Residual risk:** local test activities and a local HTTP server. A real remote system that commits after the abort is, by definition, not proven; the idempotency key only helps if the receiving service honours it. A `job` activity relies on the job reaching a terminal state; a job whose cancel is never acknowledged ends uncertain and is not resubmitted.

### F14 Remembered sign-in is cleared after a reload and a token refresh (P2)

* **Reproduced:** yes. `tests/web/remember_auth.test.mjs` run against the pre-fix `client.js` fails 4 of its 6 scenarios.

A session that was not remembered never reaches localStorage.

## Out-of-scope items we did not implement: scope decision

The review lists items that the requirements document asks for and that the project documents as missing. We checked each against the code on 9 October. None was implemented by the remediation, and one statement needed a precise wording (connection types).

| Item | Code check | Recommendation |
|---|---|---|
| JDBC/ODBC gateway | no gateway or server of any kind (`jdbc` appears only as a denied Spark data source and in two remediation hints) | **Narrow the claim**: OLCF has no JDBC/ODBC access; SQL is REST, SDK, CLI, UI and MCP only. |
| General database connection types | the connection record accepts any `type` string and stores its config and secret reference, but only `local`, `s3`, `minio`, `adls`, `onelake` have a storage provider and a connectivity test; any other type is "validated only". Two `notebookutils` remediation texts suggest "a JDBC OLCF connection", which does not exist as a working path | **Narrow the claim** to storage connections; correct the two hint texts (code change, not done here). |
| Catalog hierarchy (views, functions, schemas) and Hive/REST/Glue/Unity adapters | `catalog/` has tables, lineage and search only | **Narrow the claim**: a flat table catalog over lakehouse folders. |
| Full Iceberg management | `storage/iceberg.py` discovers and reads metadata; no compaction, snapshot expiry or partition-evolution management | **Narrow the claim** to discovery and read; Delta is the managed format. |
| Scala/R/C# cells | preserved and reported as warnings, not executed (`notebooks/formats.py`). Scala/Java *applications* (jar jobs, `source.main_class`) do run through `spark-submit` or Livy | **Narrow the claim**: Python and Spark SQL cells; Scala/Java as jar jobs. |
| Signed MSI / deb / rpm | none; the release workflow signs the wheel, sdist, installers and images with sigstore | **Narrow the claim**; do not call the Windows path "signed installer". |
| Spark RPC authentication and encryption | **not implemented** (see above) | **Narrow the claim** and require a private network between cluster nodes, or implement before multi-tenant use. |
| Section 34 performance targets | no benchmark or load test exists | **Say "targets, not measurements"** (already in the README); publish nothing until measured. |
| PostgreSQL multi-node HA drills in a real deployment | `tests/ops/test_ha.py` starts several control-plane processes on one PostgreSQL server (takeover measured at 15.9 s after SIGKILL); no multi-machine or managed-database drill | **Narrow the claim** to "tested with processes on one host". |
| Per-pool OS/container isolation | the sandbox hook is per worker agent; there is no per-pool policy object; the Kubernetes provider gives container isolation per job only when used | **Narrow the claim**: not a multi-tenant sandbox. |

Release recommendation: until the P1 fixes have been confirmed on the systems they concern (a Kubernetes cluster with an enforcing CNI, a Livy endpoint, Windows, macOS, a PostgreSQL deployment), publish OLCF 0.1.x as a beta with the supported combinations written down, keep the Kubernetes, Livy, Fabric and Windows paths labelled experimental, and state the narrowed scope above in the README and the release notes.
