## How to read this page

* Base path `/v1`. Send `Authorization: Bearer <token>` (a login access token or a personal access token, see `olcf login` and `olcf token create` in the [CLI guide](../guides/cli.md)). Exceptions are listed under **hooks** (the credential is in the request) and the health probes.
* Errors use one envelope: `{"error": {"code", "message", "details", "remediation", "correlation_id"}}`; see [Error codes](errors.md).
* Lists return `{"items": [...], "next_cursor": ...}`; mutating long-running calls return `202` with a job or operation id and accept an `Idempotency-Key` header; updates use `ETag` / `If-Match`.
* **Permissions checked** is the result of a *static* scan of the handler source for `require(...)`/`can(...)` calls. A handler may delegate further checks to a service it calls (for example per-workspace checks on the stored object), so the list is a lower bound; an operation without a list performs its checks in the service layer (or needs only an authenticated caller). The role to permission mapping is in [Permissions and roles](permissions.md).
* The MCP endpoint (`/mcp`) is mounted at the application root and is described in the [MCP guide](../guides/mcp.md).
* The interactive explorer of a running server is `/v1/docs`.

### `GET /v1/health/ready`

Readiness: 503 when the database does not answer or when production trusts the public development runtime-signing key (``runtime-trust`` is ``down``). The body of a 503 is the same fixed document in both cases: the probe is unauthenticated, so it says *that* the node is not ready, never *why* (the reason is in ``GET /v1/admin/health``, ``olcf health`` and ``olcf status``). Liveness (``GET /v1/health``) is unaffected, so an orchestrator keeps the process but stops routing to it.

Responses: `200` any. Errors use the standard envelope (`422` validation, `401`, `403`, `404`, `409`, `412`, `429` as applicable).
