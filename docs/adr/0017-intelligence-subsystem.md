# ADR 0017: Intelligence is an optional, observe-only module that builds its own asset graph

Status: Accepted

## Context

The platform already had a **catalog**: `catalog_entries` (one row per lakehouse table with statistics and tags), `table_stats` and `lineage_edges` (table-to-table edges that SQL and copy activities recorded when they ran). It answers "which tables exist" and, for work that ran through those two paths, "what was read to write this table". It cannot answer the questions people actually ask:

* *Where does the number in this dashboard tile come from?* (a report, a model, a notebook and a file are not catalog entries; there is no column level and no way to say how sure an edge is);
* *What breaks if I change this column?* (needs the code that has not run yet, not only the code that has);
* *Why is this table stale?* (needs write times and run outcomes along the chain);
* *What is unused?*, *where does PII end up?* (need a model of sensitivity, ownership and exposure; the catalog has no classification model).

Those questions need a graph of heterogeneous things (workspaces, lakehouses, tables, columns, notebooks, pipelines, activities, saved queries, dashboards, Power BI models, measures, reports), with identities that survive renames and re-scans, and edges that carry **how they are known** (observed, parsed, assumed) and **why**. The same graph has to be fed from OLCF's own storage and compute, and from Microsoft Fabric and Power BI, which OLCF extends but does not control.

Constraints that came with the platform: the control plane must keep working when anything new is broken ([ADR 0002](0002-database-as-state-and-leader-lease.md) makes the database the single state store); read paths are read-only by default ([ADR 0006](0006-read-only-sql-engines.md), [ADR 0014](0014-mcp-read-only-by-default.md)); credentials for other systems are secrets ([ADR 0007](0007-envelope-encrypted-secrets.md)); the same code must run on SQLite and PostgreSQL ([ADR 0011](0011-sqlalchemy-core-two-databases.md)); and Fabric is an adapter, not a re-implementation ([ADR 0001](0001-fabric-as-an-adapter.md)).

## Decision

**1. A module on the common platform.** Intelligence is the package `olcf.intelligence`, registered like every other module (`api/modules.py`), with its own database tables in three migration streams (the graph, discovery, governance), its own REST routes under `/v1/intelligence` and `/v1/governance`, settings (`[intelligence]`, `[governance]` and runtime settings), permissions, health checks, events and audit actions. It runs inside the control-plane process on the leader's loops. It is optional: `intelligence.enabled = false` stops collection and the rest of the platform does not notice.

**2. One-way dependencies and failure isolation.** Nothing in the compute path imports it. Outside the module it is named only by the two registration lists, the MCP tool modules and the sample installer, which look the service up by name while it is installed (the sample does it through the service only; it does not import the package); an import-graph test fails the build if `compute`, `worker`, `runtime_lib`, `sql`, `pipelines`, `catalog`, `storage`, `notebooks` or `fabric` import it. The module's core imports only `core`, `db`, `security` and the HTTP helpers every router uses; the discovery connectors may read other parts of the platform (the classic catalog's tables, the Fabric adapter's token and HTTP code, the pipelines' leader-loop helper), and the SQL analyzer reads the SQL function allowlist. The platform talks to the module **only through events**: compute, SQL and pipelines publish `dataset.*` and `pipeline.run.*` events through `core/dataset_events.py` in a best-effort block, and the module consumes them from a durable `inbox` table. The subscriber only appends; it never raises into the publisher and backs off after repeated failures. The event bus delivers to each in-process subscriber on a lane of its own and a publisher waits for its subscribers for at most 0.5 seconds in total (`core/events.py`), so even a hung subscriber costs a job state change, a statement or a pipeline run no more than that. A broken inbox or graph must leave jobs, queries and pipelines unchanged (`tests/intelligence/test_isolation.py`). The price, accepted: events can be lost, and a verified edge can be missing.

**3. Observe-only.** Discovery reads definitions, metadata and run-time reports; it never writes to the systems it observes, never changes a job, and the module never sits on the execution path. Governance (glossary, domains, data products, owners, classifications, certification, policies) is observe-only too: a policy has a mode and the only mode is `observe`; `enforce` is refused with `422 unsupported`. A violation is a record and an event, not a block. Enforcement, if wanted, is built from events and webhooks outside, or by a later decision that supersedes this one.

**4. An asset graph with stable ids, aliases and honest edges.**

* Every asset has an id `ast_<ULID>` that never changes. What other tools call the same thing is recorded as **aliases** `(kind, value)`, unique across the graph (an OLCF item id, a lakehouse table, a Fabric `<tenant>/<workspace>/<item>`, a OneLake path, a Delta location, a qualified name, a Power BI object id, ...). Resolution is by alias, then by default-lakehouse qualification, then by a unique qualified name in the workspace, and otherwise creates a **placeholder** that is merged into the real asset when a scan finds it. Assets and edges are **never deleted**: absence in a succeeded full scan marks them `removed`.
* Edges (`READS_FROM`, `WRITES_TO`, `TRANSFORMS`, `DEPENDS_ON`, `USES_MEASURE`, `DISPLAYS`, `CONTAINS`, `EXECUTES`) join datasets *through the process that moves the data* (a notebook, a pipeline activity, a saved query, a job); column lineage is `TRANSFORMS` with the process in `via`.
* Every edge has a **confidence** (`verified` only from observation at run time; `derived` from parsing a definition, metadata or a catalog record; `inferred` where an assumption was needed; `unknown` exists in the vocabulary and is not emitted) and **evidence** (who saw it, where, when; redacted and capped). A path is as strong as its weakest edge. Run-time observation upgrades a derived edge and keeps it verified for `intelligence.verified_evidence_days`.
* What could not be read is stored as a **gap** with a kind, the subject, the reason and how to fix it. Answers carry the gaps that touch them. A scan that had blocking gaps ends `partial` and never removes anything; only a succeeded full scan sweeps.
* Analyzers are **pure** (no database, network or file system; no user code executed or imported), deterministic, bounded and never raise. They return plain records; one engine turns records into rows.

**5. Layered over the existing catalog, not replacing it.** The classic catalog is unchanged and keeps its routes, CLI and MCP tools. The `local` source mirrors `lineage_edges` into the graph (as `derived` edges with source `catalog-mirror`), and an optional `catalog_mirror` source mirrors `catalog_entries`. Intelligence never writes to the catalog's tables. The word "catalog" now has three meanings (the classic catalog, the Spark catalog name of a lakehouse, the console's **Data catalog** page over the graph); the concepts page says which is which.

**6. Visibility is part of the model.** Reads are filtered to the caller's workspaces; a hidden asset answers `404`; traversal stops at the boundary; evidence through a hidden asset is returned as hidden; workspace-less assets need organisation-wide `intelligence.read`. See the [security model](../concepts/security-model.md#intelligence-discovery-lineage-and-sampling).

**7. Sampling is separate, opt-in and never stored.** Metadata discovery and data reading use different permissions (`intelligence.manage` vs `intelligence.sample`) and, for Fabric, different identities. Off by default; a policy (scope, rows 0..100, masking, exclusion of classified columns) must allow it; values are never stored; the audit record holds column names only.

**8. MCP: read-only, narrow, and without data values (extends [ADR 0014](0014-mcp-read-only-by-default.md)).**

* The module adds 10 `intel_*` tools (`intel_search_assets`, `intel_get_asset`, `intel_lineage`, `intel_where_does_this_come_from`, `intel_impact_analysis`, `intel_staleness`, `intel_documentation`, `intel_coverage_gaps`, `intel_summary`, `intel_unused_assets`) and, when governance is installed, 4 `governance_*` tools (`governance_glossary_search`, `governance_asset`, `governance_exposure`, `governance_quality`). With them the endpoint exposes **29** tools (ADR 0014 counted 15), **27** of them readable with the `mcp` scope; the two that change state are still the job tools behind `mcp:write`.
* All 14 new tools are read-only, need `intelligence.read` through a token of scope `mcp`, are listed only while the module is installed, use the caller's visibility and are capped like every MCP result.
* There is **no MCP tool** for the sample endpoint, for changing a source, a scan, a policy, a label, a certification or an approval. The REST write and sample routes refuse an `mcp` token even when its owner is an administrator. An agent that wants values uses `run_sql`, under the SQL guard and its owner's rights, which is where the decision belongs.
* Answers are built for a model: compact references, one-sentence `summary`, per-statement confidence and evidence summary, the gaps that make the picture incomplete, and `complete: false` when the answer is a lower bound.

## Consequences

* The five questions have answers that say how sure they are and what is missing. The module is also a larger surface: 24 tables (8 for the graph, 2 for discovery, 14 for governance), 129 REST operations (36 under `/v1/intelligence`, 93 under `/v1/governance`), one more set of permissions, and a graph that grows (assets, aliases, edges and gaps are kept; the attribute history of an asset is not trimmed in this version).
* Lineage is **incomplete by construction**. Static analysis reads text; it cannot know a parameter's runtime value, a UDF's body or a dynamic table name, and says so with gaps. Verified edges exist only for work the platform ran and the probe covers (PySpark, host Python with delta-rs and DuckDB, every SQL statement through the SQL service, pipeline copies); work Fabric runs in its own engine is never verified.
* A verified edge is a report from the job's own process. User code can lie within the lakehouses attached to the job; the control plane validates and clips but cannot make the runner honest.
* **Fabric and Power BI behaviour follows Microsoft's documentation.** The connector and the scanner import are covered through a local test server (`tests/fabric/fabric_fakes.py`). Tenant differences are listed in [the guide](../guides/intelligence.md#what-to-check-on-first-contact-with-your-tenant) and [release readiness](../development/release-readiness.md).
* Endpoint overrides of a Fabric source (`config.network`) are SSRF-guarded: https only, no credentials in the URL, no loopback, private, link-local or metadata destination, checked when the source is saved and again before every use, with connections pinned to the address that was checked. The runtime setting `intelligence.allow_private_endpoints` (default `false`) lifts only the loopback and private block, for private-link gateways and test doubles; while it is on, the service principal's credential goes to those endpoints. Behind a proxy only a local name check is possible. Overrides also need `integration.fabric.manage`.
* A restricted reader sees shorter lineage than an administrator and cannot be told that something was hidden.
* Because the module depends on the platform only through events, there is a lag between a run and its verified edge, and compute does not wait for it.
* Governance cannot block anything. A deployment that needs enforcement must build it from `governance.violation.opened` and webhooks.
* Two pre-existing documents are now outdated and were corrected or noted: ADR 0014's tool counts (see its note) and the sentence in the MCP guide that said *verified* included values "read from metadata".

## Alternatives considered

**Embed lineage in Spark execution** (a Spark listener or the query plan on every job). It gives accurate, column-level lineage for what ran on Spark, with no parsing. Rejected as the *only* mechanism because (a) it sees only work that ran, never the notebook that has not run yet or the report that reads the table; (b) OLCF also runs DuckDB, host Python and pure SQL services that are not Spark; (c) it would couple compute to the lineage store. The decision keeps what is good in it: the runner reports what really ran (the probe in the job process and the SQL service), as events, which upgrade parsed edges to verified.

**Reuse `catalog_entries` and `lineage_edges` as the graph.** Cheapest, and there is no second table index to keep consistent. Rejected because the schema is one-kind (tables), has no stable asset identity across renames, no aliases, no column or report or model level, no confidence or evidence, no gaps, and no history; widening it would have changed a published catalog API and its MCP tools. The catalog is instead mirrored into the graph and left unchanged.

**An external catalog (DataHub, OpenMetadata, Microsoft Purview).** These are serious products with years of connector work, mature governance workflows, a community and, in Purview's case, first-party scanning of Fabric and Power BI inside Microsoft's own trust boundary; a team that already runs one, or whose tenant already uses Purview, has a good reason to keep using it and should not rebuild it here. Rejected as the *built-in* answer for this platform because OLCF is meant to run as one installation (a laptop, one VM, or a small cluster) with no extra services; the open-source catalogs bring their own storage and search stack to operate; none of them can observe OLCF's own jobs and SQL without an integration that OLCF would have to write and maintain anyway; and the visibility model, secrets handling and audit would then live in a second system. This decision does not preclude them. The graph is available as JSON through the REST API with confidence and evidence, so it can feed another catalog. An exporter (for example OpenLineage events from the same `dataset.*` events) is **not part of this release** and would be a new module.
