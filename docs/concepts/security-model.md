# Security model

This page describes what the platform enforces, where, and where it deliberately does not try. The hardening steps for an installation are in [hardening](../operations/hardening.md); the identity provider setup is in [SSO and identity](../guides/sso-and-identity.md). The permission and role tables are generated from code in the [permissions reference](../reference/permissions.md).

## Principles

1. **The server decides.** Every API call is authorised in the server. Hiding a button in the UI is never a security boundary.
2. **Deny by default.** A request without a valid credential is `401`; a valid credential without the needed permission is `403`. A role grants a fixed set of permissions; unknown token scopes grant nothing.
3. **Authorise in the owner's workspace.** An object is always checked against the workspace it belongs to, never against a workspace id the client sends. A reference from one object to another (a job naming a secret, a connection, a lakehouse) is checked in the target's workspace.
4. **Secrets are references.** Items, connections, exports, job records, logs, audit records and capsules carry `sec_...` ids, never values.
5. **User code is trusted compute, not a sandboxed guest.** A notebook or Spark job runs as the OS user of the worker agent. OLCF offers a [sandbox hook](#code-execution), not a built-in sandbox.

## Authentication

| Credential | Format | Lifetime | Stored as | Used by |
|---|---|---|---|---|
| Access token | HS256 JWT (`iss=olcf`, `aud=olcf-api`, claims `sub`, `kind`, `scp`, `jti`, `fam`) | `auth.access_token_ttl_seconds`, default 1800 s | not stored; its `jti` or session `fam` goes into `revoked_tokens` when revoked | browser UI, `olcf login` |
| Refresh token | opaque, `olcf_...` | `auth.refresh_token_ttl_seconds`, default 14 days; single use, rotated on every refresh | SHA-256 only | browser UI, `olcf login` |
| Personal or service token | `olcf_pat_<id>_<secret>` | `ttl_days`, default 90, up to 3650 | SHA-256 of the secret only; shown once | SDK, CLI, MCP agents, Fabric notebooks, automation |
| Enrollment token | `olcf_enr_...` | single use, expires (default 1 h) | SHA-256 only | worker enrollment |
| Worker token | `olcf_wrk_...` | until revoked or renewed; optionally a maximum age (`compute.worker_token_max_age_days`, default `0` = no expiry) | SHA-256 only | worker WebSocket channel |
| Job or kernel token (derived) | scope `job`, bound to one attempt or kernel session | the job's timeout plus one hour at most; refused as soon as its attempt, job or session has ended, and revoked when the job ends | SHA-256 only; carries the persisted [credential ceiling](#job-and-kernel-credentials) | a running job or kernel calling the API (child runs, notebookutils secrets, SQL) |
| External token | Entra ID or OIDC JWT | the provider's | not stored | users of a configured identity provider, Fabric notebooks |

**Local accounts.** Passwords are hashed with scrypt (N=2^15, r=8, p=1, 16-byte random salt) and compared in constant time. An unknown user burns the same hashing time as a known one, so the response time does not reveal which names exist. The minimum length is `auth.password_min_length` (12). The bootstrap administrator is created by `olcf init` with a generated 20-character password in `<data_dir>/secrets/bootstrap-admin.txt` (or the value of `OLCF_BOOTSTRAP_ADMIN_PASSWORD`); an account flagged `must_change_password` receives a session that can call only `POST /v1/identity/password`. Local login can be turned off (`auth.local_login_enabled=false`) once an identity provider is working; the diagnostics check `lockout-guard` warns when no enabled non-local PlatformAdmin would remain.

**Brute-force limits.** Login is limited per client address (`auth.login_rate_limit_per_minute`, default 20) and per user name (10 attempts per window, reset by a successful login). Failures are audited as `auth.login_failed`. The limiter is in memory, per control-plane node. There is no account lockout. The MCP endpoint has its own per-principal limit (`mcp.rate_limit_per_minute`, default 120) and webhook triggers a per-trigger limit.

**Sessions and logout.** All access tokens of one login share a session id (`fam`). `POST /v1/identity/logout` revokes the access token it was called with and the whole session, and the refresh token if one is sent. Revocation is written to the database, so it holds on every node; a node caches the list for at most 2 seconds, so a revocation made on another node can take up to that long to apply. Presenting a refresh token that was already rotated, more than 10 seconds after the rotation (shorter reuse is treated as two browser tabs racing), is treated as theft: the whole session is revoked and `auth.refresh_reuse_detected` is audited. Changing a password revokes the account's refresh tokens; already issued access tokens live until they expire (at most the access TTL). Personal tokens are revoked individually (`olcf token revoke`) and take effect on the next request. **Revoking the credential a job or kernel was submitted with (logging out, revoking the PAT) also ends the callbacks of everything derived from it** (see [below](#job-and-kernel-credentials)); submit long-running work with a service token.

**Signing keys.** Access tokens are signed with a key from the JWT key ring and carry its `kid`; verification picks the key by `kid`. The ring lives in the database and its keys are wrapped with the root master key (the legacy `<data_dir>/secrets/jwt-signing.key` seeds the ring on first use). Rotation is an operation: `olcf security rotate jwt-signing-key` (see [Key rotation](#key-rotation)).

**External identities.** OIDC and Microsoft Entra ID tokens are validated against the provider's keys, issuer and audience. A federated user becomes a principal on first login; roles come from the mapping rules of the identity provider and are re-synchronised on each login (bindings with source `oidc:<name>`). Entra tokens presented by the Fabric adapter map to a principal named `fabric:<tid>:<oid>` of kind `fabric` with the narrow `fabric` scope. An optional LDAP bridge exists for group lookups. See [SSO and identity](../guides/sso-and-identity.md).

## Authorisation

Authorisation is role-based with scopes.

* A **permission** is a string such as `job.submit` or `lakehouse.destructive` (the full catalogue is in the [permissions reference](../reference/permissions.md)).
* A **role** is a fixed set of permissions. There are eight: `PlatformAdmin` (all), `SecurityAdmin`, `RuntimeAdmin`, `WorkspaceAdmin`, `Contributor`, `Operator`, `Viewer` and `ServicePrincipal`.
* A **binding** grants a role to a principal at a scope: the organisation, a workspace, an item, a connection, a runtime or a pool. An organisation-scope binding applies everywhere; a workspace-scope binding applies to that workspace.
* A **token scope** can only narrow. A principal's effective permission is the intersection of what its bindings grant and what the credential's scopes allow. The scopes are `*`, `read`, `write`, `mcp`, `mcp:write`, `fabric`, `worker` and `job`. `write` excludes platform, identity, audit, admin, `secret.manage`, `compute.manage` and `runtime.manage` permissions, so a leaked `write` token cannot administer the platform even if its owner is a PlatformAdmin.
* Every authenticated principal with at least one binding also holds `runtime.read`, so a workspace Viewer can see the runtime list that job forms need.

**No privilege escalation.** The platform-level roles (`PlatformAdmin`, `SecurityAdmin`, `RuntimeAdmin`) can be granted, or taken over from another account, only by someone who holds every permission of the role, token scopes included. A SecurityAdmin can manage users and roles but can neither create PlatformAdmins nor RuntimeAdmins, nor modify, disable or reset the credentials of an account that outranks them. Workspace-class roles are granted by `identity.manage` (organisation scope) or `workspace.members.manage` (workspace scope).

**Binding cache.** Role bindings are cached for 3 seconds per node and the cache is invalidated on every write on that node, so a role change on another node is effective within 3 seconds.

**Workspace isolation.** Listing endpoints filter by the workspaces where the caller holds the permission. Lakehouses, items, connections, secrets, jobs and pipeline runs belong to one workspace, and cross-workspace references are rejected at creation time and again at launch.

## Secrets

Secret values live only in the secret store, in the `secrets` table, sealed with envelope encryption: a random data key per secret encrypts the value with AES-256-GCM, and the data key is wrapped with a master key (AES-256-GCM, with the key id as associated data). The master key comes from `OLCF_MASTER_KEY` (base64, 32 bytes), the OS keyring when `security.use_keyring` is on, or the 0600 file `<data_dir>/secrets/master.key` (or `security.master_key_file`). Master-key rotation is an operation with a resumable re-encryption of all secrets (see [Key rotation](#key-rotation)). The `vault` provider stores values in HashiCorp Vault KV v2 and takes its token from `OLCF_VAULT_TOKEN`.

Values are resolved at the moment of use by the service that needs them, are written to 0600 files on the worker for the duration of a job, and are removed afterwards. API responses return the secret's metadata only; there is no endpoint that returns a value to a user. Rotation creates a new version and audits `secret.rotated`.

**Redaction.** Logs, error details, audit details, telemetry and support bundles pass through a redaction layer (`olcf.core.redaction`). It removes bearer tokens, JWTs, `olcf_pat_`, `olcf_wrk_`, `olcf_enr_` and `olcf_hook_` tokens, private key blocks, Azure account keys and SAS signatures, AWS access key ids, credentials in URLs, and values assigned to keys named like `password`, `secret`, `token`, `api_key`, `authorization` or `client_secret`. Redaction is pattern-based: a secret printed by user code in an unusual form can survive it. Treat job logs as sensitive.

## Audit

Security-relevant actions write a record to the `audit_log` table: who (principal, source, address), what (action, resource, workspace), outcome (`success`, `failure` or `denied`), correlation id and redacted details. The catalogue includes logins and failures, token creation and revocation, user and binding changes, secret changes, configuration changes, workspace and item lifecycle, runtime and worker operations, job submissions and cancellations, destructive data operations, Fabric submissions, backups, restores and updates. Modules add further `<domain>.<verb>` actions; the list in code is not exhaustive.

With `security.audit_hash_chain` (default on), each record stores `hash = SHA-256(prev_hash || canonical JSON of the record)`. `GET /v1/audit/verify` (`olcf audit verify`; UI: Security, Audit log) walks the chain and returns the first sequence number where a record was changed or removed in the middle. The chain makes edits detectable by a reader who trusts the latest head hash; it does not stop a database administrator from rewriting the whole chain, so export to a SIEM (`GET /v1/audit/export` or `olcf audit export`, as JSONL or CEF) if you need that guarantee. Records older than `retention.audit_days` (730) are purged by the retention job; verification then starts at the first remaining record.

## Job and kernel credentials

A running job, a notebook kernel and a pipeline run call the API back (child runs, secrets for `notebookutils`, SQL, lakehouse access). They do this with a **derived credential**, not with the submitting user's token, and a derived credential can never be more than the submitter's:

* **Ceiling at submission.** When work is submitted, the credential it was submitted with is recorded as a *ceiling* in the job (`spec.credential`), session or pipeline run: the permissions that credential's scopes allow at that moment, the one workspace it is bound to, and the origin credential (PAT id or login session) at the root. A restricted PAT therefore yields a restricted job; a job that submits a child job cannot hand the child more than it holds itself.
* **Minted per attempt.** The token carries only the minimum scope `job` and is bound to one attempt of one job (or to one kernel session). Its effective permissions on every request are the intersection of the `job` scope, the stored ceiling and the owner's role bindings *as they are now*, locked to the job's workspace. Demoting the owner affects jobs that are already running.
* **Lifetime.** The token expires after the job's timeout plus one hour, and is refused as soon as the origin credential was revoked (logout, PAT revoked), the job moved to another attempt or reached a terminal state, or the kernel session ended. A malformed ceiling fails closed (no permissions). A job submitted before ceilings were persisted gets a read-only legacy ceiling after the upgrade.
* **Secrets are re-authorised at dispatch.** A job that references secrets requires `secret.use` of its owner (current bindings, ceiling and workspace) at the moment the token is minted, not only at submission.
* **Minting is bounded.** `POST /v1/identity/tokens` refuses a token whose scopes grant more than the calling token holds (`403`, "a token cannot mint a token with scopes that exceed its own"), and a restricted token cannot mint an unrestricted one.
* **Pooled SQL kernels.** The hidden sessions that run Spark SQL for the SQL editor and MCP are shared by every user of a workspace, so their credential carries nothing of the user who happened to start the pool: a fixed read-only ceiling (`workspace.read`, `item.read`, `connection.read`, `lakehouse.read`, `sql.execute`, `job.read`) in that workspace.
* **Pipelines.** A pipeline run stores the credential it was started with; when that origin is revoked mid-run, the run fails with `credential_revoked`.

What this does not do: a derived credential limits the *API* rights of the callback token. The notebook code still runs as the OS user of the worker agent and can read the job's own `job.json` (token and resolved secrets) and, on a shared worker, whatever that user can read (see [Code execution](#code-execution)).

## Key rotation

The secrets master key and the JWT signing key live in a **key ring** in the database. A ring key has a stage: `primary` (used for new data and tokens), `overlap` (still decrypts or verifies) or `retired`. Ring keys are wrapped with the root master key (`OLCF_MASTER_KEY`, the OS keyring or `secrets/master.key`), so a clean machine needs only the root key. Rotation needs the permission `admin.keys` (roles PlatformAdmin and SecurityAdmin) and is audited (`security.master_key.rotated|reencrypted|dropped|rolled_back`, `security.jwt_key.rotated|dropped|rolled_back`, the re-wrap of the ring, and the refused attempts as `*_refused`). Key material is never returned by an API. Operating steps are in the [runbook](../operations/runbook.md#rotating-credentials).

* **Master key.** `olcf security rotate master-key` adds a new primary key and starts a resumable re-encryption of every secret (compare-and-swap per row, so a concurrent secret write is not lost; unreadable rows are reported as failed). `drop-old` is refused while any secret still uses the key. `rollback` is possible until `drop-old`. When the root key comes from `OLCF_MASTER_KEY` or a file, the API rotates ring keys *under* it; the root key itself is replaced by adding the new value to the environment variable, restarting nodes one by one, running `rewrap` and removing the old value.
* **JWT signing key.** Rotation adds a key; tokens signed with the previous key keep verifying until `drop-old`, which is refused until the longest token lifetime has passed unless `--force` (which signs users out).
* **Multiple nodes.** Every node re-reads the ring every few seconds (`OLCF_KEYRING_REFRESH_SECONDS`, default 5) and at once on an unknown key id. Writes are serialised (PostgreSQL advisory lock, SQLite `BEGIN IMMEDIATE`). This was tested with threads, processes and a single PostgreSQL 16 server, not with a multi-node deployment.
* **Visibility.** `olcf security keys`, the `key-rotation` health check.

## Certificate and token renewal for workers

Worker certificates are valid for `compute.worker_cert_lifetime_days` (90) and are renewed by the agent over its authenticated control channel when fewer than `compute.worker_cert_renew_before_days` (30) remain, with random jitter; `compute.worker_cert_auto_renew=false` leaves renewal to `olcf worker renew`. The renewal replaces the token and certificate (the key pair is generated on the node, the subject is always `CN=<worker id>`); the superseded pair stays valid until the node connects with the new one or `compute.worker_token_grace_seconds` (24 h) passes, so a lost response does not lock the node out. Worker tokens never expire unless `compute.worker_token_max_age_days` is set. Expiry dates appear in `GET /v1/workers`, the `worker-certificates` health check and the alert rules `auth-expiry` and `worker-certificate-critical`. The renewal protocol was tested over plain HTTP with fake agents and against a local server; the mTLS handshake with a renewed certificate has not been exercised end to end.

## Transport security and PKI

* **TLS.** `tls.enabled=true` serves HTTPS. With no `tls.cert_file` and `tls.key_file`, a certificate is issued from the built-in CA for the host names in `server.public_url` and `tls.extra_sans`, and re-issued when the names change or fewer than 30 days remain. Supply your own certificate for production. With TLS on, `Strict-Transport-Security` (one year, include subdomains) is sent.
* **Built-in CA.** EC P-256, 10 years, key in `<data_dir>/pki/ca.key` (0600). It signs the server certificate and the worker certificates. Back it up (it is part of a backup) and keep it off shared storage.
* **Worker identity.** At enrollment the agent generates its own key and sends a CSR; the private key never leaves the node. The control plane returns a client certificate. With `tls.require_client_cert_for_workers`, the WebSocket must present a certificate whose common name matches the worker id from the token (close code 4403 otherwise). Revoked serials are refused.
* **Response headers.** Every response carries `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cross-Origin-Opener-Policy: same-origin`. UI documents also carry a Content-Security-Policy (`default-src 'self'; script-src 'self'; frame-ancestors 'none'; ...`) and `X-Frame-Options: DENY`. API responses are `Cache-Control: no-store`. CORS is closed unless `server.cors_origins` lists origins.

## Input guards

| Guard | Where | What it stops |
|---|---|---|
| SQL guard | SQL service, dashboards, MCP, pooled Spark SQL sessions | exactly one statement; reads only on the DuckDB engine; DuckDB connection locked (no external access, configuration frozen); typed parameters bound, never interpolated. The **host guard** (`olcf.sql.guard`) applies to **every role, writers included**: it refuses constructs that reach the host or the network from inside a query (Spark `REFLECT`/`JAVA_METHOD`, `TRANSFORM ... USING`, file-path tables and `LOCATION`/`DIRECTORY` clauses, `CREATE FUNCTION`, `SET`, `ADD JAR`, `${...}` substitution, every Spark function that is not on the approved-function allowlist or is called qualified, and every table function not on an allowlist, for both Spark SQL and DuckDB; text that cannot be parsed as one statement is never forwarded). The rendered SQL is checked again before it runs |
| Path confinement | local storage provider, uploads, workspace import | a lakehouse root or path outside the workspace's directory, a granted `local` connection root or `storage.local_allowed_roots`; `..` traversal; archive entries escaping the extraction root |
| SSRF guard | `http` pipeline activity, outbound webhooks, alert channels | loopback, RFC 1918, link-local (including 169.254.169.254), CGNAT, multicast and reserved addresses, with every resolved address checked at connect time (no DNS rebinding gap) and redirects covered; operators allow or deny ranges with `network.ssrf.allow`, `network.ssrf.deny` and `network.ssrf.block_private` |
| Idempotency and ETags | job submission, item updates | duplicate submissions (`Idempotency-Key`) and lost updates (`If-Match`, `412`) |

| Git secret scan | Git commit | refuses to push files or messages that contain secret-like strings |

## Code execution

Notebook cells, Spark jobs and scripts execute arbitrary code. The platform controls who may submit it (`job.submit`, `session.use`), in which workspace and with which secrets and connections, but once running, the code has the rights of the worker agent's OS user. Consequences:

* Run workers as a dedicated unprivileged user, on hosts that do not hold other secrets.
* Jobs run in their own process group in a per-job working directory; Spark and kernels run from the installed runtime directory.
* An administrator may set a **sandbox command** on a worker agent (`sandbox_command` in the agent configuration, or `--sandbox-command`): a command prefix, such as `bwrap` or a container runner, that wraps every job command, with `{workdir}`, `{runtime_dir}`, `{state_dir}` and `{home}` substituted. If it is configured and not installed, the job fails; it is never run unsandboxed. The wrapper must leave the network between driver, executors and master intact. OLCF ships no profile and does not test specific sandboxes.
* Python and jar dependencies of an environment are installed only from approved indexes and are hash-locked (`security.allow_public_package_install`, `security.allowed_package_indexes`); a per-workspace environment setting can tighten but not loosen this. Hash locking proves the bytes are those that were resolved, not that the package is benign.

## Supply chain

Runtime manifests are signed with Ed25519 and verified before install; every wheel and jar in a runtime is pinned by hash. The signing key bundled with the source tree (key id `8ea01f731883a91d`) is a development key: **its private half is in the repository**, so a manifest signed with it proves nothing about origin. **Production installations trust only their own key.** The development key is trusted only when the installation's `environment` is not `production` (the default when `config.toml` does not say) or when `runtime.trust.allow_development_key = true` is set explicitly; `olcf init` and `olcf quickstart` write `environment = "development"` for local use. `runtime.trust.dir` (or `OLCF_RUNTIME_TRUST_DIR`, which wins) points at a directory of operator-managed public keys that replaces the built-in store, managed with `python -m olcf.runtime trust list|add|remove`. The `runtime-trust` health check reports the state. The shipped manifests are signed with the development key, so a production installation must re-sign them with its own key; see [hardening](../operations/hardening.md#6-supply-chain) and [runtime management](../guides/cluster-and-control-panel.md#runtimes). Fabric capsules are signed with a per-submission HMAC and cannot be replayed (see the [Fabric extension model](fabric-extension-model.md#the-call-flow)).

## Intelligence: discovery, lineage and sampling

The Intelligence module ([concepts](intelligence.md), [guide](../guides/intelligence.md), [ADR 0017](../adr/0017-intelligence-subsystem.md)) builds a graph of everything it can read about your data estate. Three things make it security relevant: it holds **credentials** for other systems (a Fabric tenant), it can read **data values** (sampling), and a lineage graph can disclose facts about assets a reader may not open. What it enforces:

**Permissions.** Five permissions were added (the full matrix is generated in [permissions](../reference/permissions.md)): `intelligence.read` (browse assets, lineage, impact, documentation, gaps), `intelligence.manage` (sources, scans, imports, sampling policies), `intelligence.sample` (read policy-limited sample rows), `governance.curate` and `governance.approve`. `intelligence.read` is held by PlatformAdmin, SecurityAdmin, WorkspaceAdmin, Contributor, Viewer and ServicePrincipal (not by Operator or RuntimeAdmin); `intelligence.manage` and `governance.approve` by PlatformAdmin, SecurityAdmin and WorkspaceAdmin; `intelligence.sample` only by PlatformAdmin and WorkspaceAdmin. A token of scope `mcp` or `mcp:write` carries only `intelligence.read`.

**Visibility (lineage as an information-disclosure channel).** Every read is filtered to the workspaces the caller can read. An asset in another workspace answers `404`, exactly like one that does not exist; a lineage or impact walk does not enter it and returns no placeholder, so hidden neighbours cannot be counted; evidence that passes through a hidden asset is returned as `{"hidden": true}` and member counts of data products report `hidden_members` as a number only. Assets that belong to no workspace (a tenant, an external system, an imported scanner result) need an organisation-wide `intelligence.read`. A source's configuration is shown only to an organisation-wide `intelligence.manage`. The price is stated: a restricted user sees shorter lineage and cannot be told that something was left out. `tests/intelligence/test_visibility.py` pins the rules for assets, edges, snapshots and evidence.

**Discovery-source credentials.** The credential of a Fabric source (a client secret, or a private key and certificate) is accepted only as write-only input, stored in the platform secret store ([Secrets](#secrets)) and referenced by a `sec_...` id in the source, or the source references an existing service-principal connection. It is never returned by any endpoint, never logged, never put in an audit record, and resolved to memory only for the duration of one scan or connectivity test. On the command line it can come from an environment variable, standard input, a certificate file or a hidden prompt; never from an argument. Connectivity-test output shows token *claims*, not tokens. Gap texts, evidence snippets, names and URL aliases pass through the redaction layer, and a saved scanner result that looks like it contains a credential is refused on import. Changing the network endpoints of a source (`config.network`) needs `integration.fabric.manage`, because the credential is sent to those hosts.

**Sampling.** Metadata discovery and data sampling use different permissions and, for Fabric, different identities. Sampling is **off** until a policy with `max_rows > 0` exists; the narrowest scope wins (asset, source, workspace, global); rows are clamped to 100; every cell is masked (`none`, `hash`, `redact` or `partial`); classified columns and columns that look sensitive are left out by default; a column is governed by its parent table's policy and automatic value profiling during a scan asks the same policy service (a table-level ban means zero storage reads, a failed classification lookup fails closed); nothing is cached or stored; the audit record `intelligence.sample_read` holds the asset, the number of rows, the column *names*, the masking and the policy scope, never a value. The sample endpoint refuses an `mcp` token and no MCP tool returns sample values. The metadata identity of a Fabric source cannot sample; only a separately configured sampling identity can.

**Run-time events are untrusted input.** Jobs report which datasets they read and wrote from inside user code. The control plane keeps only documented keys, clips every string, strips query strings from URIs, accepts a `lakehouse_id` only if that lakehouse is attached to the job, takes the process, workspace and engine from the job record rather than the event, takes the Fabric identifiers (tenant, workspace and notebook GUIDs, the GUIDs of an attached Fabric lakehouse) that tie a run to the tenant-scanned assets from the job's Fabric origin and the lakehouse definition and never from the events the job's code reports, and forwards at most 200 events per job attempt. The events carry names, never values, and the statement text delivered to in-process subscribers is not stored in the event table.

**Analyzers read hostile text.** Definitions (notebooks, SQL, pipelines, models, reports, scanner results) are attacker-influenced input. The analyzers never execute or import it, touch no database, network or file system, and have hard caps on size, nesting and result count (see [lineage support](../reference/lineage-support.md)); a construct that hits a cap is recorded as a gap. URLs found in analysed code (an `http` pipeline activity, a Power Query `Web.Contents`) are **recorded as names, never fetched**.

**MCP exposure.** The 10 `intel_*` and 4 `governance_*` tools are read-only, require `intelligence.read` through a token of scope `mcp`, are not listed when the module is off, use the caller's visibility, cap their output, and are logged like every MCP call. There is deliberately no tool for sample rows, source changes, scans, policies, labels or approvals ([ADR 0014](../adr/0014-mcp-read-only-by-default.md), extended by [ADR 0017](../adr/0017-intelligence-subsystem.md)).

**Governance is observe-only.** Labels, certification and policies are records; nothing on the execution path consults them. Four-eyes approval for classifications (`governance.classification_four_eyes`) and the refusal of self-approval (`governance.allow_self_approval`) are settings; suggestions from detectors are never approved automatically.

### Threat model for Intelligence

| Threat | Mitigation | Residual risk |
|---|---|---|
| Theft or leak of the scanner's Entra credential | Write-only input; stored sealed in the secret store; referenced by id; never returned, logged or audited; certificate authentication is supported; short-lived tokens obtained per scan | Whoever holds `secret.manage` on the platform or the master key can read it. The service principal's own reach in Fabric is whatever you granted it |
| Scanner identity over-privileged | Metadata and sampling identities are separate; the scanner issues only read operations; tenant settings are enabled for a security group | Reading a Fabric item definition needs the **Contributor** role (documented by Microsoft), which grants write on the workspace. OLCF does not write, but a stolen credential could |
| Sample values leak (to a user, an agent, a log) | Default off; permission plus policy; row cap 100; masking; classified and sensitive-looking columns excluded; no storage; audit holds names only; no MCP tool; MCP tokens refused on the endpoint | Masking `none` and `partial` still disclose; the heuristics that exclude sensitive columns miss names they do not know (for example a fully lower-case run-together `customerssn`). Policy is the control, not the heuristic |
| Lineage discloses assets the reader cannot open | Workspace-scoped reads; `404` for hidden assets; traversal stops at the boundary; hidden evidence redacted; org-wide read for workspace-less assets | A name and a relationship in the *shared* part of the graph are visible to anyone who can read the workspace they belong to. Alias values (paths, URLs) are workspace-scoped data: do not put secrets in names |
| SSRF through source URLs | Analysed URLs are never fetched. The only outbound hosts are the configured Microsoft endpoints. A long-running-operation `Location` from the Fabric API is refused if it points to another host than the configured Fabric endpoint. Endpoint overrides need `integration.fabric.manage`. Every endpoint a Fabric or Power BI source contacts (`authority_host`, `fabric_api`, `powerbi_api`, `onelake_dfs`, and a `proxy` named in the source) must be https without credentials in the URL and must not resolve to a loopback, private, link-local or cloud-metadata address. The check runs at create and update (422 with a remediation) and again at use, before a token is requested; connections then resolve the name themselves, check every address and connect to the address they checked, so a DNS answer that changes between the check and the connection is refused, and redirects are not followed | The runtime setting `intelligence.allow_private_endpoints` (default `false`) lifts the loopback / private-range block, and allows plain http to such addresses, for private-link gateways and test doubles: while it is on, anyone who may set `config.network` can aim the control plane, with the service principal's credential, at an internal host. The metadata endpoint (169.254.169.254) and the other link-local and reserved ranges stay blocked either way. Behind a proxy (a source's own or `HTTPS_PROXY`) the proxy resolves the destination, so the connect-time pin is not possible: the names are checked locally only. Keep `integration.fabric.manage` to PlatformAdmin |
| Poisoned lineage by a job (forged `dataset.*` events) | Validation and clipping; attached lakehouses only; process from the job record; 200 events per attempt | Code running in a job can lie about what it read or wrote *within the lakehouses attached to it*. A **verified** edge proves that the runner reported it, not that the code is honest |
| Denial of service by a huge or adversarial definition | Pure, bounded analyzers; per-source scan lease; `intelligence.max_concurrent_scans`; analysis cache by etag; lineage answers cut at `intelligence.max_lineage_nodes`; the SQL parser's pathological join case is refused | No benchmark exists at scale. A very large estate can still make a scan slow |
| Credentials inside a saved scanner result | Validation refuses a document that looks like it contains a credential | Pattern based: an unusual form can pass. The document is stored compressed in the source row and is not returned by the API |
| Event inbox flooded or lost | Durable inbox with a bounded batch; the subscriber never raises into the publisher and backs off; health check on depth and lag | Events are best effort: they can be lost, and a verified edge can be missing. Compute never waits for Intelligence |
| Unauthorised change of governance state | `governance.curate` / `governance.approve`; four-eyes and no self-approval as settings; every action audited; ETags on updates | Observe-only: a violation does not block anything |

## What is not protected

Be clear about the limits when you assess the platform:

* No multi-tenancy against hostile tenants. Workspaces separate permissions and data references, not hardware. Users who may run code on a worker can read anything that worker's OS user can read, including the files of other jobs on the same node.
* Data in lakehouses is not encrypted by OLCF; use the storage provider's encryption. SQLite database contents other than secret values are not encrypted.
* The rate limiter is per node and in memory.
* The audit chain detects partial tampering only.
* OLCF does not enable Spark RPC authentication or encryption between master, driver and executors (user code cannot change `spark.authenticate*`, `spark.network.crypto.*` or `spark.ssl.*`, so it cannot disable them either). Keep the Spark ports (7077, driver and block-manager ranges) on a trusted network ([ports and networking](../reference/ports-and-networking.md)).
* Execution and credentials: the callback token of a job is bounded (see [Job and kernel credentials](#job-and-kernel-credentials)), but the code itself is not isolated from the worker's OS user, and there is no per-pool OS or container isolation. A job token's id is recorded on its attempt before the launch is handed to a provider, so a launch that fails or is re-queued has its token revoked at once; a token that reached a worker is revoked when its attempt ends, and is refused once its attempt is no longer live (the expiry of job timeout plus one hour only matters if the control plane crashes between minting and recording).
* Intelligence: the Fabric and Power BI connector, the scanner import and Fabric sampling follow the assumptions in [Fabric assumptions](../guides/fabric-assumptions.md); `config.network` endpoint overrides are checked against private, link-local and metadata addresses unless `intelligence.allow_private_endpoints` is turned on; a verified lineage edge is a report by the job's own process, not proof of what its code did; governance is observe-only and enforces nothing.

Report vulnerabilities as described in [SECURITY.md](../../SECURITY.md).
