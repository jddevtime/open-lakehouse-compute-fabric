# Release readiness

OLCF 0.1.0 is a **beta for evaluation on trusted infrastructure with trusted-user compute** (no operating-system sandbox between users' code). This page is the checklist of what has to be done and
validated before each kind of claim or publication. A row stays `NOT DONE` until the acceptance test has been run and its result recorded (service versions, topology,
observed output); passing local tests does not close a row, because the acceptance tests need systems outside the test suite (GitHub Actions, a Fabric tenant, Kubernetes with an enforcing CNI, a
Livy gateway, Windows and macOS hosts).

*Timing* says which claim or publication the row blocks, so that optional features do not all have to become prerequisites for publishing a narrowly scoped beta of the source repository.

## Release sequence

1. Review the applied changes and the unresolved broad-test results. Preserve the original ZIP and the latest edited source separately.
2. Choose and apply the real GitHub owner and repository. Run `python scripts/check_release_config.py` until it passes. Confirm the private reporting contact and the repository controls (R01).
3. Publish the source as a scoped beta only after all relevant local checks are green. Keep Kubernetes, Livy, Fabric (including Intelligence's Fabric and Power BI discovery, R15) and Windows claims marked experimental until their checks are done.
4. Run the complete GitHub dry run from an immutable commit, including the required Python, Spark, browser, Windows, PostgreSQL, deployment and security jobs. Triage every failure and every unexpected skip (R02).
5. Complete the live acceptance exercises for each feature that will be advertised as supported (R05 to R10, R15 to R17). Record the service versions, topology and observed results.
6. Provision private runtime signing (R03), review license notices and advisory findings, and build fresh artifacts from the final immutable source. Verify both Python distributions (`olcf` and `olcf-fabric`) independently.
7. Tag the approved version, inspect all artifacts and signatures, and check the draft release installation instructions on clean machines. Remember that the tag pipeline can already publish versioned GHCR images (approve the `release` environment only when you want them).
8. Publish the reviewed draft only when ready. Enable PyPI trusted publishing (`PUBLISH_PYPI=true`) only after both projects and the protected `pypi` environment are configured. Keep a rollback and advisory-response procedure available.
