# Changelog

All notable changes to Open Lakehouse Compute Fabric are documented in this file.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Until 1.0.0, minor versions (0.x) may contain breaking changes; they are called out under *Changed* or *Removed*.

## [Unreleased]

### Added

* **Python notebooks without Spark.** Every worker offers the built-in `olcf-host-python` runtime (its own Python interpreter, no Spark, engine `python`). A Python-engine notebook, job or session whose Spark runtime is not installed runs on it (`compute.host_python_fallback`, on by default; Spark work never does); the job records the node's fingerprint, the `runtime_fallback` event and, in `result.json`, the library versions. Switch off per node with `olcf-worker run --no-host-python`.
* **Queued jobs explain themselves.** `queue_reason` (`code`, `message`, `remediation`) on the job record, a `queue_reason` timeline event, `waiting:` / `fix:` lines in `olcf job status|get|--wait`, and a waiting banner on the console's job page.
* The `plots` extra (`matplotlib`) for the charts of the sample notebook `02_Retail_Explore_Python`, which now needs only `deltalake`, `duckdb` and `pandas`; `ipykernel` and `pandas` are base dependencies.
* **OLCF Intelligence** (new module, `olcf.intelligence`): an asset catalog and graph with stable `ast_` ids, table and column lineage with a confidence and evidence on every edge, gaps recorded as data, schema history, freshness and impact analysis, an unused-table report, and an observe-only governance layer (business glossary, domains, data products, owners, sensitivity labels with a review queue and propagation along lineage, certification, seven policy rule types, quality score). Static analyzers read SQL, PySpark, notebooks, OLCF and Fabric pipelines, Spark job definitions, OLCF dashboards, semantic models (TMDL, DAX, Power Query M) and Power BI reports; run-time `dataset.*` events from jobs, SQL and pipelines produce `verified` edges and reach the module only through a durable inbox, so compute, SQL and pipelines cannot fail or wait because of it. Sources: the local installation, the classic catalog (read-only), a Microsoft Fabric / Power BI tenant (service principal; Fabric REST, OneLake Delta logs, Power BI admin scanner) and imported scanner results. Sampling of values is off by default and policy-controlled. Surfaces: 129 REST operations under `/v1/intelligence` and `/v1/governance`, `olcf intelligence` and `olcf governance`, `client.intelligence` and `client.governance` in the SDK, 10 `intel_*` and 4 `governance_*` read-only MCP tools, and five console areas. Runs submitted from a Fabric notebook attach to the notebook and tables a tenant scan found (by the Fabric ids the job carries, `verified`, or by name, `inferred`); the endpoints of a Fabric source are SSRF-guarded (`intelligence.allow_private_endpoints`, default off, lifts the loopback and private block); failed event rows are retried once (`intelligence.inbox_retry_after_minutes`) and can be re-queued (`olcf intelligence inbox requeue`, `POST /v1/intelligence/inbox/requeue`, audit `intelligence.inbox_requeued`, migration `intelligence` 2 adds `inbox.updated_at`); impact has its own bound (`intelligence.max_impact_nodes`) and attribute history is trimmed (`intelligence.max_versions_per_asset`). New permissions `intelligence.read`, `intelligence.manage`, `intelligence.sample`, `governance.curate`, `governance.approve`; 24 new tables; settings under `intelligence.*` and `governance.*`; `OLCF_DATASET_EVENTS=0` switches the job probe off. The sample workspace is scanned on install and gets a glossary, a domain, a data product, a PII label and certifications, plus a synthetic Power BI scan labelled as invented. Documentation: [concept](docs/concepts/intelligence.md), [deployment shapes](docs/concepts/intelligence-fabric-and-onprem.md), [guide](docs/guides/intelligence.md), [lineage support matrix](docs/reference/lineage-support.md), [ADR 0017](docs/adr/0017-intelligence-subsystem.md), readiness items R15 to R18.
* **Intelligence in the first-run sample (sample version 4).** When the Intelligence module is installed, `olcf sample install` (and the installer behind the console) also scans the sample, imports a clearly labelled *synthetic* Power BI scanner result (`schemas/sample-retail-powerbi-scan.json`: a model over the gold tables, two reports, 11 measures) as a `scanner_import` source, adds a small glossary, the domain *Retail Sales*, the data product *Retail Sales Analytics*, the approved PII label on the customer e-mail column and the certification of the gold tables - so the first look shows real answers: a visual traced back to the raw files, column lineage for every measure, the impact of a raw file. The install summary gets an `intelligence` section; without the module the sample installs as before, and a failing step never fails the install. An installation of an earlier version gets the new content with `olcf sample install --reinstall`.
* **System tests for Intelligence** (`tests/intelligence/system/`): the whole platform with the real analyzers and connectors and no stubs - the sample as one system through REST, MCP, CLI and SDK; live run-time lineage from a real worker; schema change through catalog sync, inbox, scan and certification; failure isolation; the deployment shapes (without Intelligence, without Fabric, Fabric only, Fabric plus on-premises with one asset per OneLake path); a scale test (2000 tables, 20000 columns, 5040 edges) with documented bounds; and an end-to-end authorisation matrix (a Viewer of one workspace learns nothing of another through any surface).
* **Install from GitHub.** `scripts/install.sh` installs from this repository's source archive by default (`--ref`, `--source`; pure Python, every dependency a wheel, nothing compiled) and keeps `--wheel`, `--version` with `--index-url`, and `--offline-bundle`. The uv route is `uv tool install "olcf @ https://github.com/jddevtime/open-lakehouse-compute-fabric/archive/refs/heads/main.tar.gz"`.
* **Agent-friendly repository.** `AGENTS.md`, `llms.txt` and `CLAUDE.md` tell an AI agent how to set OLCF up for a person, how to work on the code and where help is most valuable.
* **README graphics** are generated by `scripts/gen_diagrams.py` (`--check` in the tests): the architecture, the Intelligence pipeline, the Fabric extension, the three deployment modes and the capability map.
* **Third external review answered** ([`docs/dev/CODE_REVIEW_RESPONSE_3.md`](docs/dev/CODE_REVIEW_RESPONSE_3.md)): sampling and value profiling share one data-read policy; authoritative identities decide asset identity; the merge audit no longer deadlocks on SQLite; incomplete scans and analyses keep the last known lineage and never sweep; Fabric scans keep a durable retry set and a valid `modifiedSince`; paging caps and byte caps are enforced while streaming; the analysis cache includes its resolution context; Intelligence's SQLite write pacing and the event bus persist budget; the CI browser job fails instead of skipping.
* `olcf user create --must-change-password` and the matching console box; the server enforces the forced password change for every client.
* Logout revokes the whole login (`revoked_tokens`); reuse of a rotated refresh token revokes its family; `GET /v1/admin/diagnostics` answers before the first run; `GET /v1/workspaces/{ws}/pipelines` lists pipelines with their last run and triggers.

### Changed

* **Unsafe runtime trust fails readiness.** `runtime-trust` is a critical health check: a production installation that trusts the public development runtime-signing key now makes `GET /v1/health/ready` answer `503` (fixed body, no detail; liveness `GET /v1/health` stays `200`). Development, `olcf quickstart` and production with an operator trust directory are unaffected. The Helm readiness probe now calls `/v1/health/ready` (the `olcf-healthcheck` script takes an optional path).
* The traceability matrix has a new section 41 for Intelligence (30 rows) and the total moved from 269 to 299 rows; the statements that the platform has no classification model were corrected (rows 7.2, 29.1, 29.4, Known limitation 22). The ADR 0014 read-only MCP decision is extended to the `intel_*` and `governance_*` tools.
* `scripts/gen_reference.py` also finds audit actions written as `self.audit(principal, "...")`, so the `governance.*` actions appear in the generated [events reference](docs/reference/events.md).
* `olcf quickstart` reports a working state (URL, one-time credentials, dashboard link, next commands) before it installs the Spark runtime, which is now a non-fatal follow-up with a retry command; a stale CLI token from another data directory is replaced.
* CLI failures print `error:` and `hint:` instead of a traceback (`-v` restores it). `olcf restore` restores into the data directory; `olcf backup create --include-keys` includes the certificate authority.
* The Spark smoke test runs on the real cluster and reports executors per node; `compute.reserve_cores` is live; agent signals run the graceful shutdown (`--keep-daemons-on-exit` replaces `stop_daemons_on_exit`).
* The rate limiter is bounded; settings layers merge key by key; `pytest tests` collects in one invocation.
* Key ring writes are serialized (PostgreSQL advisory lock / SQLite `BEGIN IMMEDIATE`): concurrent rotations from threads, processes or nodes can no longer lose a key. The local `olcf runtime` commands and `quickstart` trust the development runtime-signing key exactly when the installation's own `config.toml` does, and an older installation whose `config.toml` has no `environment` is told, in one message, how to fix it (`olcf init`, `olcf serve`, `olcf runtime install`, the server log).
* A Spark cluster start waits no longer than its job: cancelling the job or closing the provider ends the launch waits; compute locks are per database object.

* **The event bus delivers through one lane per subscriber** (`olcf.core.events`). A subscriber that hangs, is slow or raises no longer holds up the publisher or the other subscribers: `publish` persists the event, hands it to every lane and waits at most `WAIT_BUDGET` (0.5 s) in total for the lanes it handed it to; a lane keeps its own order and is bounded (`LANE_CAPACITY` 10000; when it overflows the oldest queued delivery is dropped and counted, the event itself stays in the table) and a subscriber that publishes from its own lane does not wait for lanes. Before, publishers called subscribers in turn and a subscriber that blocked for seconds blocked every job-state change behind it.
* **Intelligence inbox: one attempt per row per pass.** A row that fails is retried on the next pass of the processor, not three times in a row inside one pass, so a graph that is briefly unavailable no longer turns a row into `failed` within a single tick. A `failed` row is queued once more automatically after `intelligence.inbox_retry_after_minutes` (30), and an operator can queue every failed row again with `olcf intelligence inbox requeue`.
* **Run-time lineage of an item-less python job** is typed `script` (it was typed as a Spark job whatever the engine). Only `engine = spark` makes a `spark_job` process.
* **Intelligence registry:** a column reference that carries the physical location of its table (`scope["table_alias"]`, written by every analyzer) now resolves the table by that location. Before, a notebook that read a OneLake path another source had already reported left an orphan placeholder table next to the real one; its edges were right, only the extra empty asset and its `unresolved_reference` gap were wrong.
* The Intelligence group in the console sidebar is shown only when the server offers `/v1/intelligence/summary` (`hasRoute`); on an installation without the module there is no dead navigation. The command palette follows the same check.

### Security

* **A password you choose is never printed or stored.** `olcf init`, `olcf quickstart` and the first start of `olcf serve` used to echo an administrator password supplied through `--admin-password-stdin`, `OLCF_ADMIN_PASSWORD` or `OLCF_BOOTSTRAP_ADMIN_PASSWORD` and to write it to `secrets/bootstrap-admin.txt`, so a container logged it. A supplied password is now neither shown nor saved; a generated one is still shown once and saved as before. Found by the container workflow's log check on its first run; `tests/tooling/test_init_password_echo.py` covers it.

The 18 findings of the external review of 8 October 2026 are answered one by one in [`docs/dev/CODE_REVIEW_RESPONSE.md`](docs/dev/CODE_REVIEW_RESPONSE.md) (what was reproduced, what changed, which tests, what remains open).

* **Job and kernel credentials can no longer exceed the submitter's (F01).** The credential a job, notebook kernel or pipeline run calls the API back with is derived from the credential it was submitted with: capped by its stored ceiling, by the owner's current role bindings and by the single workspace, bound to one attempt or kernel session, and refused after the origin PAT or login was revoked. `POST /v1/identity/tokens` refuses a token that asks for more than the calling token holds. Pooled hidden SQL kernels carry a fixed read-only credential. Secrets a job references are re-authorised at dispatch.
* **SQL cannot reach the host (F02).** A host guard refuses Spark `REFLECT`/`JAVA_METHOD`, `TRANSFORM ... USING`, file-path queries, `LOCATION` and `DIRECTORY` clauses, `CREATE FUNCTION`, `SET`, `ADD JAR`, `${...}` substitution, denied scalar functions and every table function outside an allowlist (Spark and DuckDB) for **every role**, and checks the rendered SQL again.
* **Spark SQL functions are an allowlist (C01).** `olcf.sql.spark_functions.SPARK_ALLOWED_FUNCTIONS` lists the approved built-ins; unknown/UDF and qualified function calls fail closed (run a notebook or job instead), and the permissive unparsed-text fallback for writers is gone: every role needs exactly one fully parsed, supported statement.
* The development runtime-signing key is no longer trusted by default in production (see Changed).

### Release-readiness follow-up (second review, 9 October 2026)

The applied changes C01 to C14 of the second review were re-implemented here, test first; see [`docs/dev/CODE_REVIEW_RESPONSE_2.md`](docs/dev/CODE_REVIEW_RESPONSE_2.md) for the finding-by-finding answer, the places where this tree differs from the report, and what is still open. Its recommendations R01 to R14 are tracked, all open, in [`docs/development/release-readiness.md`](docs/development/release-readiness.md).

* **Uncertain submissions are never replayed.** Any 5xx answer to a Livy POST is `SubmissionUncertain` after exactly one POST (reconciled by name); a pipeline HTTP call that may have been sent without an idempotency key is not repeated on 503. A cancelled HTTP call is woken by a socket shutdown and closed by the thread that owns it.
* **Release engineering.** `scripts/build_release.sh` builds the server and the Fabric SDK (wheel and sdist each), runs a source-archive gate separate from the wheel gate, refuses a non-empty output directory, and takes `--require-identity`; `scripts/check_release_config.py` is the identity preflight (it fails until the real GitHub owner and repository are set); `.gitleaks.toml` and per-line `gitleaks:allow` annotations on synthetic fixtures; reusable CI, container and security workflows that gate the release build; draft releases, 0.x prereleases, `latest=false`, and a separate PyPI workflow (`PUBLISH_PYPI`). None of the workflows has run on GitHub.
* **Chart and probes.** The Helm readiness probe now calls `/v1/health/ready`; the docs no longer name a `/v1/health/live` route that does not exist.
* Verified on Linux on 9 October 2026: unit 62, web 1, integration 13, data 911, orch 398, items 184, compute 478, node 343, fabric 282, corpus 54, ops 124, security 383, tooling 383 and the Spark-marked tests (integration 2, compute 2, node 18, fabric 1, corpus 10) passed, e2e 55 passed; ruff, mypy (cli, sdk), `check_docs`, the five `gen_*.py --check` and `check_headers` are clean; gitleaks 8.24.2 finds nothing in the tree; `actionlint` 1.7.12 passes on the workflows; a clean-wheel `olcf quickstart` ran the sample notebook. Occasional timeouts of the installer tests (cold downloads through the sandbox proxy) and one connection reset in `test_streams.py` under heavy parallel load passed on re-run.

### Added (review remediation)

* `olcf security keys` and `olcf security rotate master-key|jwt-signing-key` (REST `GET /v1/admin/security/keys`, `POST /v1/admin/security/rotate/{master-key|jwt-signing-key}`, permission `admin.keys`): key rings in the database, resumable re-encryption, `drop-old` and `rollback`; the `key-rotation` health check.
* Worker certificate and token renewal: automatic inside the renewal window, `olcf worker renew`, `POST /v1/workers/{id}/renew`, optional `compute.worker_token_max_age_days`, expiry fields, the `worker-certificates` health check and the alert rules `auth-expiry` and `worker-certificate-critical`.
* `olcf compute smoke` is asynchronous (202 and polling, `--wait/--no-wait`, `--status`, `--cancel`, `--timeout`, `--server-timeout`); exit codes 0 passed, 10 failed or timed out on the controller, 11 the command stopped waiting; `409 no_spark_runtime` and `smoke_already_running` answer 6.
* A queued Python-engine job is re-bound to the host Python runtime when its runtime is available on no online worker (`runtime_fallback` with `rebound: true`).
* `python -m olcf.runtime trust list|add|remove`, the `runtime.trust.*` settings and the `runtime-trust` health check.
* Kubernetes: the job Secret is mounted read-only at `/opt/olcf/input` and staged into a writable `emptyDir` at `/opt/olcf/work` (`--workdir`); non-root pods; the runner delivers an explicit `result` event, the artifacts and a termination record; a pod that ends without a result fails with `result_missing`; log reading uses a timestamp cursor and reports gaps (`log_gap`).
* Livy: sessions and batches are named `olcf-<job>-a<attempt>`, ambiguous POST failures are reconciled instead of retried (`submission_adopted`, `submission_not_created`, `submission_unresolved`), `JobSource.main_class` and `args`, Spark `conf` is passed through, statements are split lexically, notebook parameters are injected by the same helper as the agent runner.
* `GET /v1/admin/ports` lists every Spark port range; the Helm values `spark.ports.*` drive both the ConfigMap and the NetworkPolicy, which now also opens the master, worker daemon and driver UI ports and gained `networkPolicy.monitoring.*`, `egress.*` and `workerIngressFrom`.
* `restore_reconcile`: unfinished jobs of a restored database are marked failed; the `restore-test` report gets `jobs` and `job-reconcile`.
* A cross-platform file lock (`olcf.core.filelock`), a CI job `windows`, `OLCF_TEST_ORDER`, `uv venv --seed` in CI and a `PipMissing` error with a remediation.

### Changed (behaviour)

* **Logging out, or revoking the PAT a job was submitted with, ends that job's callbacks** (state, results, lakehouse access). Submit long-running jobs with a service token.
* **Production no longer trusts the development runtime key.** An installation whose `config.toml` has no `environment` is `production`, so after the upgrade the bundled runtime manifests are refused ("not trusted") until you re-sign them with your own key and set `runtime.trust.dir` / `OLCF_RUNTIME_TRUST_DIR` (control plane and external agents), or, on a development machine, add `environment = "development"`. `olcf init` and `olcf quickstart` write it. The Docker `BAKE_RUNTIME` build argument failed for the same reason; it now trusts the development key only in the throwaway build stage (try-out images) or installs an operator-signed manifest with the `RUNTIME_TRUST_DIR` build argument, the final image stays `production`, and the Helm chart mounts a trust directory (`runtimeTrust.existingSecret|existingConfigMap`). The installers run `olcf init` before the runtime install.
* **`olcf compute smoke` exits 9 (not 11) when the client stops waiting**, as the CLI exit-code table says; `status` and `doctor` show a `runtime-trust` that is `down` or `degraded` as a warning with the fix; `ComputeService.run_spark_sql` refuses `ADD JAR`, `ADD FILE`, `RESET`, `CACHE TABLE` and the other session commands for every caller; a token minted for a failed job launch is revoked immediately.
* **Derived credentials are capped**: a job that used to create items or write beyond the submitting token's scopes now gets only the intersection (a restricted PAT yields a restricted job); jobs queued before the upgrade get a read-only ceiling.
* **Pipeline timeouts**: a timeout enters a cancelling phase and waits up to `policy.cancelGraceSeconds` (default 30) for the activity to stop. An activity that did not stop, or whose outcome is unknown, ends as `timeout_uncertain` and is retried only if idempotent (`policy.idempotent`, an idempotent activity class, or an `http` request with an `Idempotency-Key`); otherwise the run fails with `details.operatorAction` and waits for `POST /v1/pipeline-runs/{id}/resume`. A non-idempotent activity that times out no longer retries on its own. Event `pipeline.activity.outcome_uncertain` and the metric `olcf_pipeline_activity_outcome_uncertain_total`.
* **Helm**: ports come from `spark.ports.*`; the worker daemon RPC and UI ports are now pinned from ranges (41200-41299, 41300-41399) and the driver UI range is 4040-4056; the restrictive egress branch (`networkPolicy.egressAllowAll=false`) was rewritten (DNS, database, HTTPS, API server, workers, monitoring, `extra`).
* Livy batches read `source.main_class` and `source.args` (not `parameters.main_class/args`); a jar without `main_class` is refused.
* A Python-engine notebook run through Livy keeps the submitted parameter values (the defaults used to win); an unterminated SQL string is refused rather than split.
* The Spark smoke test is a polled operation with a deadline on the controller (`--server-timeout`, 10-1800 s, default 240); `POST /v1/compute/spark-smoke` answers `202` with a `poll_url` instead of holding the request open.
* Tests live in packages with qualified helper imports (`tests/<area>/*_support.py`); `mypy src/olcf/cli src/olcf/sdk` is clean.

### Release engineering (external review follow-up, 9 October 2026)

* **Both Python distributions are built and gated.** `scripts/build_release.sh` now also builds the Fabric SDK (`olcf-fabric`, wheel and source archive) with `LICENSE` and `NOTICE`, checks that the SDK and server versions agree, installs the SDK wheel in its own environment, writes an SBOM for each distribution and refuses a non-empty `--out` directory instead of deleting it (it is run with `bash`). `scripts/verify_dist.py` separates source-archive allowances (tests, CI files, exactly `deploy/.env.example`) from installed-wheel restrictions; private keys, databases, real env files, bytecode and tool caches are refused everywhere. Regression tests: `tests/tooling/test_release_artifacts.py`.
* **License metadata fallback.** `License: UNKNOWN`, `NONE` and `NOASSERTION` are treated as missing so that the trove classifier is used (ptyprocess is ISC); unidentified licenses still fail the notices check.
* **Release workflow.** CI, container and security are reusable workflows (`workflow_call`) and the release build needs all three; their concurrency groups include the calling workflow's name; the release script runs under `bash`; pip-audit runs with `--disable-pip --no-deps` on the resolved requirements. GitHub releases are drafts; every `0.x` tag is a prerelease and never moves the `latest` image tag (`latest=false` flavor plus the explicit stable rule); signing and images require a tag, attestation subjects are separate patterns, image signing lower-cases the owner, images use the protected `release` environment, and the release notes install the exact tag wheel and state the beta limitations. A tag push still pushes versioned images before the draft is reviewed unless the `release` environment has required reviewers. Optional PyPI upload moved to `.github/workflows/pypi.yml` (release published, `PUBLISH_PYPI=true`, checksums verified, trusted publishing for `olcf` and `olcf-fabric`).
* **Release identity preflight.** `scripts/check_release_config.py` (read-only) fails while owner, repository or contact placeholders remain in the public files; the build prints it as a warning and the release workflow requires it (`--require-identity`). The conduct and private security contacts are set. The real GitHub owner and repository are not set yet: this is the one open blocker (readiness R01). Tests: `tests/tooling/test_release_config.py`, `tests/tooling/test_release_workflows.py`.
* **Secret scanning.** `.gitleaks.toml` extends the default rules with a narrow allowlist (generated bytecode; the exact material of the public development signing key); synthetic fixture credentials carry per-line `gitleaks:allow` comments (tests stay scanned); the security workflow runs the pinned gitleaks CLI with that configuration. Example password output in the documentation is a placeholder; `.gitignore` covers local keys, env files, macOS metadata, test artifacts and `.hypothesis/`.
* **Documentation.** The README narrows the implementation claim to the core platform, drops fixed test counts and lists the known out-of-scope items; new [release readiness](docs/development/release-readiness.md) checklist (R01 to R14, none done) and an updated [release process](docs/development/release-process.md).

### Known limitations

New entries are in the [traceability list](docs/compliance/requirements-traceability.md#known-limitations). The review fixes were verified on Linux. The Helm chart cannot give pods a runtime trust directory yet. Out-of-scope items of the review (JDBC/ODBC gateway, catalog adapters, Iceberg management, Scala/R/C# cells, signed OS packages, Spark RPC encryption, benchmarks, real PostgreSQL HA drills, per-pool isolation) were not implemented; see the [scope decisions](docs/dev/CODE_REVIEW_RESPONSE.md#out-of-scope-items-we-did-not-implement-scope-decision).

## [0.1.0] - 2026-10-07

First public beta. Author: Justin Dodrill.

### Added

* **Control plane**: FastAPI application with a versioned REST API under `/v1` (OpenAPI document at `/v1/openapi.json`, Swagger UI at `/v1/docs`),
  SQLite (single node) and PostgreSQL (production) metadata stores with transactional, versioned migrations, persistent events and a
  tamper-evident audit log.
* **Identity and security**: local users, personal access tokens with scopes, eight composable roles with scoped bindings and a no-escalation rule,
  OIDC / Microsoft Entra / LDAP federation, scrypt password hashing, encrypted secret store, built-in private CA with optional mTLS for workers,
  secret redaction in logs, events, support bundles and API output.
* **Workspaces and items**: workspaces, notebooks, lakehouses, SQL queries, pipelines, environments, Spark job definitions, variable sets, schedules and
  reports; item versions with ETags, recycle bin, workspace export/import, Git sync (three-way comparison, secret scan) and deployment promotion.
* **Lakehouse and SQL**: local, S3/MinIO, ADLS Gen2 and OneLake storage providers; Delta protocol inspection with an interoperability policy, Iceberg
  discovery, maintenance with safeguards; read-only DuckDB and delegated Spark SQL engines, history, export (CSV, JSON, NDJSON, Parquet), dashboards
  with eight tile types (KPI, bar, line, area, donut, table, heatmap, scatter), catalog, search and SQL lineage.
* **Compute fabric**: worker agent with outbound WebSocket channel and reconciliation, enrolment tokens, pools, queues, cordon/drain, a leader-only
  scheduler with admission control and retry rules, Spark Standalone clusters across enrolled machines, local, external-Spark, Kubernetes and
  Fabric-Livy providers, interactive notebook sessions on real Jupyter kernels, per-job hash-pinned dependency layers.
* **Runtimes**: signed (Ed25519), hash-pinned, side-by-side Spark runtimes (`fabric-2.0-compatible`, `fabric-1.3-compatible`, `olcf-native`), transactional
  install/repair/retire/rollback, offline bundles, optional verified Temurin JDK download.
* **Microsoft Fabric compute extension**: `olcf-fabric` SDK (`run_remote`, `extend`, `test_connection`, ...), HMAC-signed execution capsule with single-use
  nonce, pull mode, deterministic compatibility analyzer (73 rules, ruleset 1.0.0), `notebookutils` shim, Entra token validation, OneLake access,
  stepwise diagnostics, submissions log and metrics.
* **Pipelines**: durable DAG engine, control-flow, notebook, Spark job, script, SQL, copy and HTTP activities, expression language, manual / cron /
  webhook / storage / dependency triggers, Fabric pipeline import (documented subset), signed outbound webhooks, alert rules and channels.
* **Operations**: encrypted backups with restore tests and off-host targets, signed updates with preflight and rollback, diagnostics and support bundles,
  retention, HA leader election, Prometheus and OTLP export, health checks with deep tests.
* **AI agents**: MCP endpoint (Streamable HTTP, protocol 2025-06-18 and 2025-03-26) with 15 tools, resources and prompts, a stdio bridge, per-call
  authorisation and audit.
* **Clients and tooling**: web console (Preact, no build step, no CDN), `olcf` CLI with about 200 commands, sync and async Python SDK,
  one-line installers for macOS/Linux/Windows that never touch Xcode stubs, Docker images and Compose profiles, Helm chart, systemd / launchd / Task Scheduler files,
  offline bundle builder, SBOM and third-party notices generation.
* **Documentation**: this documentation set, generated CLI / API / configuration / permissions / events / error / health references, 12 architecture decision
  records and a requirements traceability matrix with the evidence for each requirement.

### Known limitations

See [`docs/compliance/requirements-traceability.md`](docs/compliance/requirements-traceability.md#known-limitations). Highlights: Delta on Spark is checked by `scripts/verify_spark_delta.py` on a networked machine; Git sync has no pure-Python fallback.
